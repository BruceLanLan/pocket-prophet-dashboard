# 改造路径的完整选项空间

本文档盘点"还能怎么改造这台设备"，按 **价值 × 可行性** 排序。写作动机：此前所有工作都集中在 WiFi + 壁纸接口这**一条**通道上，而这台设备至少有四条物理通道，其余三条从未探过。

---

## 通道盘点

| 通道 | 探索状态 | 说明 |
|---|---|---|
| WiFi + `/wallpaper` HTTP 接口 | **已探明** | 四个接口，只写，且仅在"更换壁纸"界面开启时可达（ARCHITECTURE.md §1.5） |
| **BLE 蓝牙** | **完全未探索** | 产品宣传含"蓝牙翻页控制"，说明固件有 BLE HID。**可能是一条不受 WiFi 窗口限制的常驻通道** |
| **NFC** | **完全未探索** | 产品宣传含 NFC。若设备能**读**标签，那就是本项目一直缺的输入通道 |
| 串口 / SWD（拆机） | 未探索 | ESP32 系列，可只读 dump 固件，不改动任何东西 |

---

## 选项 1：BLE 通道探测（**最高优先级**）

**为什么它可能改变一切**：当前架构的全部痛苦来自"设备平时不在网上"。但 BLE 的设计初衷就是低功耗常驻广播。如果设备在待机时仍广播 BLE，就存在一条**不依赖用户打开任何界面**的通道——那"后台自动推送"就重新成立了，整个项目形态可以改回原本设想的样子。

**证据支持**：产品明确宣传"蓝牙翻页控制电子书"。翻页器要能用，必须在阅读时保持 BLE 连接，说明 BLE 在常规使用状态下是活的，而非仅存在于配置模式。

**当前阻塞**：macOS 的 TCC 权限。系统蓝牙是开的（`system_profiler` 显示 `State: On`），但 CoreBluetooth 对当前进程报告"Bluetooth device is turned off"，这是权限被拒的典型表现；`TCC.db` 受 SIP 保护无法自行授权。

**如何解除**：需要用户在自己的终端里运行扫描脚本，届时 macOS 会弹出蓝牙权限请求；或在"系统设置 → 隐私与安全性 → 蓝牙"里为终端 App 授权。

**分层推进（前两步完全被动、零风险）**：

1. **被动嗅探广播**：只监听，不连接。看设备是否在待机状态下广播，记录名称、厂商数据、服务 UUID。零风险。
2. **枚举 GATT 服务**：连接后只读服务与特征值列表。ESP32 项目常见 Nordic UART Service（`6E400001-B5A3-F393-E0A9-E50E24DCCA9E`），若存在可写特征值，即为潜在数据通道。只读，风险极低。
3. **尝试写入**：有风险，需另行评估，不在被动探测范围内。

**诚实的反面**：也可能只广播标准 HID 服务、没有任何自定义服务，那这条路就到此为止。但**第 1 步的成本是二十秒，收益是可能推翻整个架构约束**，性价比极高。

---

## 选项 2：把 Phase 0 的问题问全（零成本）

原 Phase 0 只问"推上去的图离网后还在不在"。这里补一个同等重要、却一直没被问出口的问题：

**设备停留在"更换壁纸"界面时，屏幕上显示的是什么？**

这个问题重要，是因为探测 A 已经证明：**设备停在那个界面时可以连续在线一小时以上**。也就是说存在一种"停驻模式"——把设备就搁在那个界面上不退出，它就是一台常驻联网设备，定时刷新完全可行。

- 若停驻时屏幕显示的是**壁纸本身**（或推送后会刷新成推送内容）→ **停驻模式成立**，仪表盘可以做成真正的定时刷新，代价只是耗电。
- 若停驻时屏幕显示的是**二维码/配置提示**这类界面 → 停驻模式对显示无意义，仪表盘只能依赖"离网后内容留存"。

这个问题和原有的三个问题在同一次观察里就能一并回答，**不增加任何成本**，但可能直接救活仪表盘功能。已补进 PLAN.md 的 Phase 0。

---

## 选项 3：只读 dump 固件（拆机，但不改动）

**收益最大的单一动作**。ESP32 的 `esptool.py read_flash` 是**纯读取**操作，不写入、不改动任何东西，dump 出来的固件能一次性回答目前所有悬而未决的问题：

- `COMPRESS_ARRAY_V2` 的编码算法（从此可脱离厂商云端，不必再靠猜字节）
- WiFi 为什么只在特定界面开启，是否有办法让它常驻
- BLE 到底暴露了什么服务
- 是否存在未公开的接口或调试后门

**代价**：需要拆开外壳、找到 UART 焊盘（ESP32 通常有 TX/RX/GND 测试点）、接 USB-TTL 转换器。

**风险分级**（这点必须说清楚）：
- **只读 dump**：不修改设备，风险主要在物理拆解本身（划伤外壳、扯断排线）
- **回写固件**：这才是有变砖风险的操作，**不建议**，且不在本项目范围内

如果愿意接受拆机，"只读 dump + 分析"是投入产出比最高的一步——它把所有逆向工作从黑盒猜测变成白盒阅读。

## 选项 4：NFC 通道探测（成本极低）

设备带 NFC，但用途未知。两种可能，含义天差地别：

- **设备能读取 NFC 标签** → 这就是本项目一直缺的**输入通道**。可以做到"把设备贴一下某个标签就触发起卦"，真正恢复"摇一摇"那种物理仪式感（当前方案只能从网页点按钮）
- **设备只是被读取的标签** → 价值有限，仅用于手机触碰识别

**如何测**：用 iPhone 的 NFC 功能靠近设备看是否能读到标签；或者拿一张普通 NFC 标签（门禁卡、公交卡）靠近设备，看设备有无反应。几分钟即可，无任何风险。

---

## 选项 5：劫持厂商云端（**价值可能比想象中低**）

直觉上"把 `dot.mindreset.tech` 用 DNS 指向自己的服务器"很有吸引力，但**先看清一个事实**：

转换 API 的调用是**浏览器**发出的（官方网页的 JS 里 `fetch(CONVERT_API)`），**不是设备**发出的。所以劫持这个域名只是劫持了我们自己浏览器的请求——而那部分我们本来就完全掌控。**只要能自己实现编码，根本不需要碰 DNS。**

真正有价值的变体是另一个问题：**设备自己在连网期间会不会对外发请求？**（同步运势数据、检查固件更新等）。这个可以在设备在线时抓包验证，若发现设备有自己的云端依赖，那才存在值得劫持的东西。

优先级：低。除非抓包发现设备确有主动外联。

---

## 选项 6：把目标拆到合适的硬件上（战略层）

这一条不是技术方案，是范围判断，但可能是最省力的答案。

你本地已有 **`~/m5-paper-buddy`** 项目（M5Paper V1.1，ESP32 + 墨水屏，PlatformIO 工程）。对比两台设备的适配度：

| 需求 | 口袋先知 | M5Paper |
|---|---|---|
| 环境化仪表盘（天气/行情/新闻/用量） | 设备平时不联网，需手动开界面，且屏幕仅 200×200 | 完全可编程、可常驻联网、960×540 大屏 |
| 口袋里的占卜物件（摇卦） | 正是它的产品定位，形态贴合 | 形态不对，M5Paper 是台式设备 |

**结论**：口袋先知的独特价值在于"口袋里的占卜物件"，而这恰恰就是摇卦；把"环境仪表盘"这个诉求硬塞给它，是在跟它的产品设计对抗。如果仪表盘是真实需求，M5Paper 才是对的工具，而且你已经有现成工程。

这也是 PLAN.md 把摇卦提到第一位、把四个仪表盘页面设为条件功能的深层理由。

## 推荐的下一步顺序

1. **BLE 被动扫描**（需你授权，二十秒，零风险，可能推翻整个架构约束）
2. **Phase 0 + 停驻模式观察**（一次观察回答四个问题，成本为一张壁纸，你已同意）
3. **NFC 试探**（几分钟，可能找回物理触发的仪式感）
4. 固件只读 dump（需拆机意愿，但一次性解决所有逆向问题）
5. 抓包看设备是否主动外联（低优先级）
6. 仪表盘迁移到 M5Paper（战略选项，看你实际有多想要那四页）
