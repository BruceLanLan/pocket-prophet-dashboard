# 改造路径的完整选项空间

> **范围声明（2026-07-29）**：本项目已明确定位为**官方能力扩展，不做破解**（见 README「定位」）。本文档中涉及**逆向编码格式、dump/改写固件、拆机**的选项，均为探索过程的**记录与备忘**，**全部在当前项目范围之外**。保留它们是为了不丢失已查明的事实（例如设备是 ESP32、蓝牙是模式门控），而不是把它们列为待办。当前实际推进的只有：官方上传接口做信息显示（`docs/PLAN.md`），以及可选的蓝牙翻页器当遥控器（见文末）。

本文档盘点"还能怎么改造这台设备"，按 **价值 × 可行性** 排序。写作动机：此前所有工作都集中在 WiFi + 壁纸接口这**一条**通道上，而这台设备至少有四条物理通道，其余三条从未探过。

---

## 通道盘点

| 通道 | 探索状态 | 说明 |
|---|---|---|
| WiFi + `/wallpaper` HTTP 接口 | **已探明** | 四个接口，只写，且仅在"更换壁纸"界面开启时可达（ARCHITECTURE.md §1.5） |
| **BLE 蓝牙** | **完全未探索** | 产品宣传含"蓝牙翻页控制"，说明固件有 BLE HID。**可能是一条不受 WiFi 窗口限制的常驻通道** |
| **NFC** | **完全未探索** | 产品宣传含 NFC。若设备能**读**标签，那就是本项目一直缺的输入通道 |
| 串口 / SWD（拆机） | 未探索 | ESP32 系列，可只读 dump 固件，不改动任何东西 |

## 选项 1：BLE 通道探测（**最高优先级**）

**为什么它可能改变一切**：当前架构的全部痛苦来自"设备平时不在网上"。但 BLE 的设计初衷就是低功耗常驻广播。如果设备在待机时仍广播 BLE，就存在一条**不依赖用户打开任何界面**的通道——那"后台自动推送"就重新成立了，整个项目形态可以改回原本设想的样子。

**证据支持**：产品明确宣传"蓝牙翻页控制电子书"。翻页器要能用，必须在阅读时保持 BLE 连接，说明 BLE 在常规使用状态下是活的，而非仅存在于配置模式。

**当前阻塞**：macOS 的 TCC 权限。系统蓝牙是开的（`system_profiler` 显示 `State: On`），但 CoreBluetooth 对当前进程报告"Bluetooth device is turned off"，这是权限被拒的典型表现；`TCC.db` 受 SIP 保护无法自行授权。

**如何解除**：需要用户在自己的终端里运行扫描脚本，届时 macOS 会弹出蓝牙权限请求；或在"系统设置 → 隐私与安全性 → 蓝牙"里为终端 App 授权。

**分层推进（前两步完全被动、零风险）**：

1. **被动嗅探广播**：只监听，不连接。看设备是否在待机状态下广播，记录名称、厂商数据、服务 UUID。零风险。
2. **枚举 GATT 服务**：连接后只读服务与特征值列表。ESP32 项目常见 Nordic UART Service（`6E400001-B5A3-F393-E0A9-E50E24DCCA9E`），若存在可写特征值，即为潜在数据通道。只读，风险极低。
3. **尝试写入**：有风险，需另行评估，不在被动探测范围内。

**诚实的反面**：也可能只广播标准 HID 服务、没有任何自定义服务，那这条路就到此为止。但**第 1 步的成本是二十秒，收益是可能推翻整个架构约束**，性价比极高。

---

## 选项 2：把 Phase 0 的问题问全（零成本）

原 Phase 0 只问"推上去的图离网后还在不在"。这里补一个同等重要、却一直没被问出口的问题：

**设备停留在"更换壁纸"界面时，屏幕上显示的是什么？**

这个问题重要，是因为探测 A 已经证明：**设备停在那个界面时可以连续在线一小时以上**。也就是说存在一种"停驻模式"——把设备就搁在那个界面上不退出，它就是一台常驻联网设备，定时刷新完全可行。

- 若停驻时屏幕显示的是**壁纸本身**（或推送后会刷新成推送内容）→ **停驻模式成立**，仪表盘可以做成真正的定时刷新，代价只是耗电。
- 若停驻时屏幕显示的是**二维码/配置提示**这类界面 → 停驻模式对显示无意义，仪表盘只能依赖"离网后内容留存"。

这个问题和原有的三个问题在同一次观察里就能一并回答，**不增加任何成本**，但可能直接救活仪表盘功能。已补进 PLAN.md 的 Phase 0。

---

## 选项 3：只读 dump 固件（拆机，但不改动）

**收益最大的单一动作**。ESP32 的 `esptool.py read_flash` 是**纯读取**操作，不写入、不改动任何东西，dump 出来的固件能一次性回答目前所有悬而未决的问题：

- `COMPRESS_ARRAY_V2` 的编码算法（从此可脱离厂商云端，不必再靠猜字节）
- WiFi 为什么只在特定界面开启，是否有办法让它常驻
- BLE 到底暴露了什么服务
- 是否存在未公开的接口或调试后门

**代价**：需要拆开外壳、找到 UART 焊盘（ESP32 通常有 TX/RX/GND 测试点）、接 USB-TTL 转换器。

**风险分级**（这点必须说清楚）：
- **只读 dump**：不修改设备，风险主要在物理拆解本身（划伤外壳、扯断排线）
- **回写固件**：这才是有变砖风险的操作，**不建议**，且不在本项目范围内

如果愿意接受拆机，"只读 dump + 分析"是投入产出比最高的一步——它把所有逆向工作从黑盒猜测变成白盒阅读。

---

## 选项 4：NFC 通道探测（成本极低）

设备带 NFC，但用途未知。两种可能，含义天差地别：

- **设备能读取 NFC 标签** → 这就是本项目一直缺的**输入通道**。可以做到"把设备贴一下某个标签就触发起卦"，真正恢复"摇一摇"那种物理仪式感（当前方案只能从网页点按钮）
- **设备只是被读取的标签** → 价值有限，仅用于手机触碰识别

**如何测**：用 iPhone 的 NFC 功能靠近设备看是否能读到标签；或者拿一张普通 NFC 标签（门禁卡、公交卡）靠近设备，看设备有无反应。几分钟即可，无任何风险。

---

## 选项 5：劫持厂商云端（**价值可能比想象中低**）

直觉上"把 `dot.mindreset.tech` 用 DNS 指向自己的服务器"很有吸引力，但**先看清一个事实**：

转换 API 的调用是**浏览器**发出的（官方网页的 JS 里 `fetch(CONVERT_API)`），**不是设备**发出的。所以劫持这个域名只是劫持了我们自己浏览器的请求——而那部分我们本来就完全掌控。**只要能自己实现编码，根本不需要碰 DNS。**

真正有价值的变体是另一个问题：**设备自己在连网期间会不会对外发请求？**（同步运势数据、检查固件更新等）。这个可以在设备在线时抓包验证，若发现设备有自己的云端依赖，那才存在值得劫持的东西。

优先级：低。除非抓包发现设备确有主动外联。

---

## 选项 6：把目标拆到合适的硬件上（战略层）

这一条不是技术方案，是范围判断，但可能是最省力的答案。

你本地已有 **`~/m5-paper-buddy`** 项目（M5Paper V1.1，ESP32 + 墨水屏，PlatformIO 工程）。对比两台设备的适配度：

| 需求 | 口袋先知 | M5Paper |
|---|---|---|
| 环境化仪表盘（天气/行情/新闻/用量） | 设备平时不联网，需手动开界面，且屏幕仅 200×200 | 完全可编程、可常驻联网、960×540 大屏 |
| 口袋里的占卜物件（摇卦） | 正是它的产品定位，形态贴合 | 形态不对，M5Paper 是台式设备 |

**结论**：口袋先知的独特价值在于"口袋里的占卜物件"，而这恰恰就是摇卦；把"环境仪表盘"这个诉求硬塞给它，是在跟它的产品设计对抗。如果仪表盘是真实需求，M5Paper 才是对的工具，而且你已经有现成工程。

这也是 PLAN.md 把摇卦排在构建顺序第一位的理由之一（另一个理由是它不依赖外部数据源，最快能跑通管线）。

## 推荐的下一步顺序

1. **BLE 被动扫描**（需你授权，二十秒，零风险，可能推翻整个架构约束）
2. **Phase 0 + 停驻模式观察**（一次观察回答四个问题，成本为一张壁纸，你已同意）
3. **NFC 试探**（几分钟，可能找回物理触发的仪式感）
4. 固件只读 dump（需拆机意愿，但一次性解决所有逆向问题）
5. 抓包看设备是否主动外联（低优先级）
6. 仪表盘迁移到 M5Paper（战略选项，看你实际有多想要那四页）

## 【2026-07-29 更新】选项 1 已验证并已结案：BLE 是死路

设备以 **`Rand/0 Pager`** 广播并成功配对，但**退出蓝牙翻页模式后连接立即断开**（已连接列表 → 未连接列表，HID 条目 3 → 0，彻底从系统移除）。

**结论：蓝牙与 WiFi 行为完全一致，都是模式门控，设备不存在任何常驻对外通道。** 且两者几乎必然互斥（设备一次只能停在一个界面），所以"按键触发 → 卦象立即显示"的闭环不成立。**BLE 对本项目没有可用增量。** 详见 ARCHITECTURE.md §1.6。

**但这次探索有两项持久收获：**

1. **确认硬件是 ESP32 + NimBLE 协议栈**：BLE MAC 比 WiFi MAC 大 2（ESP32 标准 MAC 分配规律），HID 属性含 `ModelNumber = "NimBLE"`
2. **发现厂商自定义 HID 通道**：描述符第三组是 Usage Page `0xFF00`、Report ID 3、1 字节任意值。说明固件里有私有协议，是固件分析时的已知靶点

## 结案后的选项重排

BLE 出局后，剩余选项的价值排序发生了根本变化：

**固件路线（原选项 3）现在是唯一能真正改变产品形态的路径。** 理由很硬：WiFi 和 BLE 的开关策略是**固件策略**，不是硬件限制——ESP32 在硬件上完全支持两者共存且常驻。也就是说，"设备平时不联网"这个卡住整个项目的根本约束，**只有改固件才能解除**。

固件路线的两级：

- **只读 dump**（`esptool.py read_flash`，不写入、不改动设备）→ 可读出 `COMPRESS_ARRAY_V2` 编码算法、私有 HID 协议、以及射频开关策略。风险仅在物理拆解本身。
- **改写固件** → 才有可能让设备常驻联网，但有变砖风险，且会失去原厂功能。**这已经超出"扩展现有系统"的范畴，接近"把它变成另一台设备"**，需要单独决策。

**其余选项的现状：**

| 选项 | 状态 |
|---|---|
| 选项 2 停驻模式观察 | 仍有效，零成本，并入 Phase 0 |
| 选项 4 NFC | 仍未探索。但鉴于 WiFi/BLE 都是模式门控，NFC 大概率同样如此，**先验价值已下调** |
| 选项 5 劫持云端 | 仍是低优先级，理由不变（转换请求由浏览器发出，非设备） |
| 选项 6 迁移到 M5Paper | **价值上升**。既然口袋先知的联网约束只能靠改固件解除，而你已有一台完全可编程、可常驻联网的 M5Paper，把"环境仪表盘"放到那台机器上，比给这台刷固件的代价小得多 |

**推荐结论**：口袋先知就按当前 PLAN.md 做成"用户触发式的摇卦设备"，这与它的产品定位一致；想要常驻刷新的仪表盘，用 M5Paper。除非你对拆机改固件本身有兴趣，否则不建议为了这四个页面去动固件。

# 附录：固件路线的具体操作

本附录回答"如果要改固件，具体怎么做"。**先读第 0 步——它可能让整件事在开始前就结束。**

## 第 0 步：先确认没有被加密锁死（决定性前置检查）

ESP32 支持 **Flash Encryption**（闪存加密）和 **Secure Boot**（安全启动）。一旦厂商在出厂时烧录了对应的 eFuse：

- **Flash Encryption 开启** → dump 出来的是密文，分析无从谈起
- **Secure Boot 开启** → 设备拒绝运行任何未经厂商签名的固件，刷不进去

这两项是**不可逆的 eFuse 位**，开了就没法关。所以**第一件事是检查，不是拆机后才发现白干**。

```bash
python3 -m esptool --port /dev/cu.usbserial-XXXX get_security_info
python3 -m espefuse --port /dev/cu.usbserial-XXXX summary
```

关注 `FLASH_CRYPT_CNT`、`SECURE_BOOT_EN`、`ABS_DONE` 等位。

**先验判断**：量产的国产 IoT 小设备**通常不开**这两项（会显著增加产线复杂度和售后成本），所以有相当机会是敞开的。但必须实测确认，不能假设。

## 第 1 步：物理连接

**需要的硬件**：

- **USB-TTL 串口转换器，必须是 3.3V 逻辑电平**（CP2102 / CH340 / FT232 均可，但务必确认是 3.3V 或可切换）。**接 5V 会烧芯片**，这是最常见的致命错误。
- 细焊台或测试夹、镊子

**需要找到的焊盘**：ESP32 模组通常在 PCB 上留有测试点

| 引脚 | 用途 |
|---|---|
| TX / RX | 串口通信（注意交叉连接：设备 TX → 转换器 RX） |
| GND | 共地，**必须接** |
| IO0 (GPIO0) | 进入下载模式的关键 |
| EN / RST | 复位 |

**进入下载模式的时序**：把 GPIO0 拉低到 GND → 复位（EN 拉低再放开）→ 松开 GPIO0。此时芯片进入 ROM 下载模式，esptool 才能通信。

## 第 2 步：只读备份（**非破坏性，务必先做**）

```bash
# 先识别芯片型号与闪存大小
python3 -m esptool --port /dev/cu.usbserial-XXXX flash_id

# 完整 dump，这一步纯读取，不改动设备任何内容
python3 -m esptool --port /dev/cu.usbserial-XXXX read_flash 0 ALL firmware_backup.bin
```

**这个备份是你唯一的后悔药，多存几份，异地存一份。** 只要它在，且 ROM 下载模式可用，设备理论上永远能恢复原状。

`flash_id` 的输出还会告诉你芯片具体是 ESP32 / ESP32-S3 / ESP32-C3 —— 这决定后续逆向用的指令集（前两者是 Xtensa，C3 是 RISC-V），Ghidra 需要装对应的处理器模块。

## 第 3 步：分析

```bash
# 分区表固定在 0x8000
python3 -m esptool image_info firmware_backup.bin

# 快速捞字符串，找 URL、接口路径、版本号
strings firmware_backup.bin | grep -iE 'http|mindreset|wallpaper|ota'
```

深入分析用 Ghidra 或 IDA。**已知的两个靶点**：

1. `COMPRESS_ARRAY_V2` 的编码算法 —— 拿到它就能脱离厂商云端
2. 射频开关策略 —— 即"为什么退出界面就关 WiFi/BLE"的那段逻辑

## 第 4 步：修改 —— 两条难度天差地别的路

### 路线 A：patch 原厂固件（保留原有功能）

在原固件里找到射频管理逻辑，改掉"退出界面即关闭"的行为，让 WiFi 常驻。

**难度：很高。** 面对的是没有源码的编译产物，需要在 Ghidra 里读汇编、定位逻辑、二进制打补丁，还要修正 ESP32 应用镜像的 SHA256 校验。对有经验的逆向工程师也是以周计的工作量。

**但这是唯一能"既解除联网限制、又保留答案之书/运势/MBTI 等原厂功能"的路。**

### 路线 B：完全重写固件

把它当成一块空白的 ESP32 + 墨水屏，用 PlatformIO/Arduino 写自己的固件——你在 `m5-paper-buddy` 上已有这套经验。

**技术上比路线 A 容易得多，但代价是原厂功能全部消失。**

主要障碍是**驱动墨水屏**：需要确定面板的控制器型号（SSD1680 / UC8151 / GDEH 系列等）和它接在哪些 GPIO 上。这要么靠 PCB 走线追踪，要么靠拆到面板上的丝印型号。这一步没有捷径。

**冷静的评估**：走完路线 B，你得到的是"一台自己完全掌控的 ESP32 墨水屏设备"——但那时你其实已经**造了一台新设备**，而不是扩展了口袋先知。考虑到你手头已有 M5Paper（同样是 ESP32 + 墨水屏、屏幕大得多、驱动现成、还有你自己的工程），为了 200×200 的屏幕走这条路，性价比是负的。

## 变砖风险的诚实评估

**ESP32 很难被真正变砖**，这是好消息，值得说清楚：它的**下载模式固化在掩膜 ROM 里，无法被擦除或覆盖**。只要你能接触到 UART 焊盘并把 GPIO0 拉低，就总能重新进入下载模式、刷回备份。这比很多其他芯片宽容得多。

真实风险按发生概率排序：

1. **Flash 加密已开启** → 第 0 步就出局，白拆（所以先检查）
2. **拆机时的物理损伤** → 划伤外壳、扯断排线、焊盘掉铜，**这是最可能的实际失败原因**
3. **没做备份就刷写** → 原厂固件永久丢失，功能再也回不来
4. **烧录 eFuse** → **永久不可逆**。绝对不要运行任何 `espefuse burn` 类命令，除非你完全清楚后果
5. **电平接错（5V 接到 3.3V 脚）** → 直接烧芯片，无法挽回

## 建议的推进方式

如果决定走这条路，按**风险递增**顺序推进，每步都可以停：

1. 拆机、找焊盘、接线 —— 不通电时零风险
2. `get_security_info` + `espefuse summary` —— **只读**，若发现加密则到此为止
3. `read_flash` 完整备份 —— **只读**，且这一步本身就有独立价值
4. 离线分析固件（找编码算法）—— 完全在电脑上进行，设备已可装回
5. 只有在前四步都顺利、且你确实想要常驻联网时，才考虑写入

**第 1–4 步不修改设备任何内容，做完可以完整装回。** 而第 3 步拿到的固件备份 + 第 4 步的编码算法，本身就足以解决"脱离厂商云端"这个问题——即使你最终不改写固件，这趟也没白跑。

## 【2026-07-29】USB/Type-C 通道：已验证为死路

用户用确认可传数据的 Type-C 线接口袋先知，USB 树与串口列表**零变化**。对照组极强：同一台 Mac、同为 ESP32 的 Cardputer 插上立刻枚举为 `USB JTAG/serial debug unit`，口袋先知插上什么都没有。

**结论：Type-C 是纯充电口**（D+/D- 未接到芯片，或固件未启用 USB 外设）。原本设想的"插线免拆机进下载模式 dump 固件"不成立。固件路线若要走，只能回到拆机焊 UART 那条路——而那已划在范围外。

## 【范围内的可选扩展】蓝牙翻页器 → Mac 实体遥控器

这是唯一一个**在官方能力内、却尚未落地**的扩展方向，记录在此备用。

设备在蓝牙翻页模式下是一个标准 BLE HID 键盘（§1.6 已确认），按键会作为键盘事件发给 Mac。因此可以把它的翻页键**重映射成任意功能**，把设备从"电子书翻页器"扩展成"桌面万能按钮"：

- 用 **Karabiner-Elements**（现成工具，零代码）把翻页键改成任意快捷键
- 或写一个监听脚本，把按键映射到任意动作：切歌、翻 PPT、触发起卦、跑任意脚本

**零破解、零风险、立即可用**，纯粹是把官方 HID 能力用到新场景。

**唯一待验证**：翻页键实际发的是什么键码（方向键？空格？Page Up/Down？）。验证方法极简单——翻页模式下把光标点进任意文本框，按翻页键看蹦出什么字符。这一步不做任何破解，只是确认官方按键的映射。

**与信息显示的关系**：两条通道互斥（§1.6），无法"按键即刻显示"。但作为独立扩展，遥控器功能完全成立，且与信息显示互不干扰——用户在不同时刻分别使用两种角色即可。
