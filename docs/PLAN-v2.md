## 优先级与顺序（可以在任何一步停下）

这一轮有 7 个阶段，**不是一个晚上的量**（Phase 8 的奇门渲染单独就是一块硬骨头）。按下列顺序推进，每完成一个都是可交付的独立增量：

| 顺序 | 阶段 | 为什么排这个位置 |
|---|---|---|
| 1 | **Phase 6** Phase 0 补做 | **阻断性**：它决定 Phase 7 能不能做 |
| 2 | **Phase 7** 自动推送 | 用户最想要的功能，但依赖 Phase 6 的结论 |
| 3 | **Phase 8** 奇门遁甲 | 全新功能，价值最高，引擎已有现成的 |
| 4 | **Phase 9** 天气图标 | 改动小、见效快 |
| 5 | **Phase 10** 行情增强 | 数据源已通，主要是版式设计 |
| 6 | **Phase 11** RSS 自定义源 | 需要新写 RSS 解析器 |
| 7 | **Phase 12** 用量页重设计 | 需要先跟用户确认预算口径 |

## Phase 6 — 补做 Phase 0（阻断性）

**它现在卡着用户最想要的功能。** 原 Phase 0 的定位是"决定各页面的体验等级"，现在升级为"决定自动推送这个形态是否成立"。

**核心问题（一次观察全部回答）**：

1. **设备停在"更换壁纸"界面时，屏幕显示的是壁纸内容，还是二维码/配置提示？** ← 这条决定 Phase 7
2. 推送后退出界面，图还在屏幕上吗？（立即 / 10 分钟 / 1 小时）
3. 设备原生内容（每日运势等）会不会覆盖它？
4. 从 POST 到画面实际变化经过多久？

**步骤**

1. 请用户在设备上打开"更换壁纸"界面
   - 验证点：`curl -s -m 5 --noproxy '*' http://<IP>/wallpaper/info` 返回 JSON
2. 推一张高辨识度测试图（大号时间戳 + 四级灰阶色块 + 四角定位标记）
   - 验证点：HTTP 200 且 `length` 变化
3. **停在该界面时，请用户看屏幕并回报**（只能由人做，不得自行推断）
4. 请用户退出界面，在三个时间点看屏幕并回报
5. 结论写入 `docs/PHASE0_FINDINGS.md`，并据此决定 Phase 7 走哪条分支

**分支**

- **结果 A｜停驻时显示壁纸** → **Phase 7 全量做**：停驻模式 + 定时轮换推送成立，这是本轮头号功能
- **结果 B｜停驻时显示配置页，但离网后壁纸持久** → **Phase 7 降级做**：不能停驻刷新，但可以做"设备一出现就自动推最新内容"的探测器，把手动步骤从"开界面+点按钮"减到"只开界面"
- **结果 C｜壁纸根本不显示** → Phase 7 取消，且需重新评估整个项目的显示前提（连摇卦也受影响）

## Phase 7 — 自动推送（形态由 Phase 6 裁定）

> **不要在 Phase 6 出结论前写这部分代码。**

### 若为结果 A：停驻模式定时轮换

1. `scheduler.py`：APScheduler 后台任务，按配置周期（默认 10 分钟，可调 5–60）轮换推送启用的页面
   - 验证点：周期临时设为 2 分钟，观察日志连续两轮推了不同页面
2. **必须有布防开关**，默认关闭。理由：设备出现的那一刻可能是用户自己想用官方页面传图，自动推送会覆盖用户操作
   - 验证点：未布防时调度器不发起任何推送
3. 沿用已有的内容哈希去重（内容没变不重复刷屏，省电省墨水屏寿命）
4. Web 界面显示布防状态、下次推送时间、上次推送结果

**两个必须写进 UI 的提醒**：

- 停驻模式要求 WiFi 常开，**设备没有电量接口，功耗完全不可测**，续航影响未知
- 布防期间不要用官方页面传自己的图，会被覆盖

### 若为结果 B：出现即推送

1. 轻量探测器：每 N 秒探活一次，发现设备上线且已布防 → 立即推送当前选定页面
2. 防抖：距上次推送不足 M 分钟则跳过
3. 同样默认关闭、需显式布防

## Phase 8 — 奇门遁甲

**可复用资产已确认可用**：`~/.agents/skills/mingli/scripts/qimen_engine.py`（1543 行，含节气定局、阴阳遁、值符值使、三盘、八门九星八神、空亡马星门迫伏吟）。实测 `datetime_to_question_pillars(now)` + `pai_full()` 能按当前时间正常起盘，返回含"地盘/天盘/人盘(八门)/九星/八神/宫位详情"等完整数据。

**版式预算（已算过）**：200×200 去掉标题栏和边距，每宫约 **63×55px**，13px 字号下每宫约 3 行 × 4 字。

**步骤（顺序重要：先验证可读性再设计版式）**

1. **先做可读性验证**：画一张九宫格 + 每宫塞 3 行单字（模拟门/星/神/干），走 `COMPRESS_RENDER` 目视确认 13px 单字在四级抖动后是否清晰
   - 验证点：目视可辨认每个字
   - **若不可读**：必须砍掉一层（建议砍八神，保留门/星/干），不要硬塞
2. `providers/qimen.py`：包装引擎，按当前时间起盘，输出渲染层需要的扁平结构
   - 静态表和排盘逻辑复用引擎，**不要重新实现**
   - 验证点：连续起盘 3 次（跨小时边界），局数/值符/值使符合引擎输出
3. **中宫处理要显式决策**：引擎有 `_handle_zhong_gong`，传统显示为"寄二宫"。渲染前确定采用哪种，并在文档写明
4. `renderer/qimen.py`：3×3 九宫格 + 顶部时间/局数 + 底部一句话
   - **不放解释文本**，200×200 放不下
   - 验证点：负载 < 8000；`COMPRESS_RENDER` 目视每宫内容不重叠、不出界
5. 接入 `app.py` 的 PAGES 注册表与首页

## Phase 11 — 要闻自定义源

**现状**：`providers/news.py` 用的是今日头条热榜接口，**那不是 RSS**。要支持"用户挑选 RSS 源"必须新写一个 RSS/Atom 解析器。

1. `providers/rss.py`：用标准库 `xml.etree` 解析 RSS 2.0 与 Atom（`feedparser` 未安装，标准库够用）
   - 验证点：对 RSS 和 Atom 各一个真实源解析出标题列表
2. 设置页支持增删 RSS 源、拖动排序（决定优先级）
3. **默认源清单必须逐个实测**——本项目已经踩过一次坑：新浪滚动新闻 RSS 早已废弃，整个 feed 只剩一条 2016 年的视频链接
   - 验证点：每个默认源都返回 ≥3 条当日/近日条目
4. 保留头条热榜作为一个可选源（它是活的且质量不错）

## Phase 12 — 用量页重设计

**必须先明确的口径问题**：用户希望"以百分比显示还剩多少用量"。**官方订阅额度百分比本地拿不到**（ARCHITECTURE.md §4.2 已确认，`.claude.json` 无任何 quota 缓存，该数据仅存在于服务端）。

**采用方案**：用户在设置里自设日预算（如 200M tokens），页面显示"今日 / 预算"的百分比，**并把预算数值显示在屏幕上**，让人一眼看出这是自设基准而非官方额度。

1. 设置页增加"每日 token 预算"字段
2. `renderer/usage.py` 重设计：环形或条形进度 + 百分比 + "预算 200M（自设）"标注
   - 验证点：目视确认无"剩余额度""官方额度"等误导性表述
3. **关于吉祥物**：Claude 没有官方吉祥物角色，有的是星芒（asterisk）标记。可画一个抽象几何符号做视觉锚点，**不虚构角色形象**
