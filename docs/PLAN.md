# 开发计划（T6 规划交接单）

> **执行模型请先读完 `docs/ARCHITECTURE.md`**，本文档中所有"已确认事实"均在该文档中有实测依据，不重复展开。
>
> 本计划按**风险与信息增益排序**：最不确定、最可能推翻整个方案的步骤排在最前。不要按功能重要性重排顺序。

---

## 目标

在 Mac 上运行一个常驻服务，通过局域网把自定义内容推送到"口袋先知"墨水屏设备，内容包括天气、股票行情、重大新闻、Claude Code 用量四类轮换页面，外加一个可触发的六爻起卦页面；所有数据源（城市、股票清单、新闻源）可通过 Web 界面自定义。

**可验收的最终状态**：服务启动后，设备按配置周期自动轮换显示四类内容；打开 Web 配置页能改数据源并立即预览；点击摇卦按钮后设备显示卦象并保持一段时间不被轮换冲掉。

---

## 约束（不可违反）

1. **`POST /wallpaper` 不可逆**。没有读回接口，`DELETE` 恢复的是出厂内建壁纸而非用户上一张图。任何写入前必须先保存源图到本地历史目录。
2. **设备是只写通道**。不要设计任何依赖"从设备读取状态/事件"的功能——接口不存在（已探测确认）。
3. **不要把 token 消耗标注为"额度"**。订阅额度百分比本地拿不到，见 ARCHITECTURE.md §4.2。渲染文案与 UI 必须区分清楚。
4. **不要复用 `meihua_engine.py` 的生克判断逻辑**（有 bug，见 ARCHITECTURE.md §4.3），静态数据表可以复用。
5. **默认节奏按小时**，不要按 10 分钟。真实节奏由 Phase 0 实测决定。
6. **不要在本期做纳甲装卦**，也不要启动 `COMPRESS_ARRAY_V2` 编码器逆向，二者均在范围外。
7. 设备 IP 必须是配置项，不允许硬编码 `192.168.3.235`。

## Phase 0 — 显示语义验证（阻断性，需用户显式同意）

**这是整个项目的地基，且是唯一需要付出不可逆代价的步骤。**

> **用户已同意覆盖当前壁纸**（2026-07-28 确认："背景图无所谓，我随时可以改"）。执行模型**不需要**再为这一具体的覆盖动作向用户确认，可以直接执行本 Phase 的步骤 1–5。下方"执行前必须向用户确认"一句对本项目已满足，保留仅作为记录该同意从何而来。

至今为止所有已确认的事实都只说明"能把数据写进设备"，**没有任何证据说明写进去的壁纸就是设备日常显示的画面**。三个未验证的子问题：

- 自定义壁纸是否为设备待机时的常显画面，还是仅为某个图层/锁屏？
- 设备自身的原生内容（每日运势、答案之书等）是否会周期性覆盖它？
- `POST` 之后面板多久实际刷新——立即、唤醒时、还是按内部定时器？

第三个问题直接决定轮换周期的真实上限。若答案是"仅在用户交互时刷新"，那么"定时轮换"这一整个产品形态不成立。

> **执行前必须向用户确认**：本步骤会覆盖设备上当前的自定义壁纸且无法找回。先请用户确认其当前壁纸的源图是否还在手上。用户未明确同意前不要执行。

**步骤**

1. 先把当前状态存档：
   - 验证点：`curl -s --noproxy '*' http://<设备IP>/wallpaper/info` 返回含 `has_custom` 的 JSON，记录 `length` 原值
2. 生成一张高辨识度测试图（200×200，含大号时间戳文字与四级灰阶色块），走云端转换：
   - 验证点：`COMPRESS_ARRAY_V2` 长度 < `max_upload`；解码 `COMPRESS_RENDER` 目视确认排版正确
3. `POST /wallpaper` 写入，并立刻开始计时：
   - 验证点：HTTP 200，且 `/wallpaper/info` 的 `length` 变为新值
4. **物理观察设备**（这一步只能由人做，执行模型必须停下来请用户看屏幕并回报）：
   - 记录：从 POST 到画面实际变化经过多久
   - 记录：不触碰设备，持续观察 1 小时，画面是否被设备原生内容覆盖
   - 记录：按一次设备按键/唤醒后，自定义画面是否还在
5. 把观测结果写入 `docs/PHASE0_FINDINGS.md`

**若失败**（画面不变、或被原生内容覆盖、或仅在交互时刷新）：**立即停止，不要继续 Phase 1**。向用户报告观测结果，本项目的推送架构需要重新设计（可能退化为"手动触发推送"而非"定时轮换"）。

## Phase 1 — 推送管线骨架

在 Phase 0 确认显示语义之后，先把最小闭环打通，再谈内容。**不要在管线未验证前并行开发五个渲染器。**

**步骤**

1. 实现 `device.py`：
   - `convert(img: PIL.Image, kernel: str) -> str` 调云端，返回 base64 负载
   - `push(payload: str, device_ip: str)` 写设备
   - `info(device_ip) -> dict` 读状态
   - 内置：推送前 `len(payload) > max_upload` 校验、内容哈希去重、最后成功负载缓存、失败指数退避
   - 每次推送前把源 PNG 存入 `history/YYYYMMDD-HHMMSS.png`
   - 验证点：对一张纯白图调 `convert`，返回长度在 40–200 之间（实测纯色图为 44–96 字符）
2. 实现 `renderer/base.py`：画布常量（200×200）、四级灰阶调色板 `{0,85,170,255}`、字体加载（`/System/Library/Fonts/STHeiti Medium.ttc`）、文本按字宽截断、分隔线等原语
   - 验证点：绘制一张含 13px 中文的测试图，解码 `COMPRESS_RENDER` 后目视可读
3. 加入"内容未变则跳过推送"的单元测试
   - 验证点：连续两次推送相同图像，第二次返回"skipped"且未产生网络请求

**若失败**：云端 API 返回非 200 时记录完整响应体后上报，不要静默重试超过 3 次。

## Phase 2 — 天气页端到端

用最简单的一类内容验证"抓取 → 渲染 → 推送"全链路。

**步骤**

1. `providers/weather.py`：抓取天气，城市可配置。选一个无需 API key 的公开源（如 wttr.in 或和风天气的免费档），把源写进配置以便替换
   - 验证点：`python3 -c "from providers.weather import fetch; print(fetch('深圳'))"` 输出含温度、天气描述、湿度的 dict
2. `renderer/weather.py`：渲染 200×200 天气页。参考版式：城市（22px）、当前温度（52px）、天气描述（18px）、湿度风力（14px 灰）、分隔线、明后两日（13px 灰）、更新时间（11px 灰）
   - 验证点：负载长度 < 5000（实测同版式为 2792）；`COMPRESS_RENDER` 目视可读
3. 串起来推一次真机
   - 验证点：设备显示天气页，内容与 `COMPRESS_RENDER` 一致

**若失败**：区分是数据源问题（provider 单测通过与否）还是渲染问题（看 `COMPRESS_RENDER`），不要笼统重试。

## Phase 3 — Web 配置界面与调度器

**步骤**

1. `config.json` schema + `config.example.json`：设备 IP、轮换周期、启用的页面及顺序、天气城市、股票清单、新闻源列表、摇卦钉住时长
   - 验证点：缺字段时以默认值启动而非崩溃
2. Flask/FastAPI 服务，Web 页面提供：编辑上述全部配置、"立即预览"（渲染并显示 `COMPRESS_RENDER`，**不推送**）、"立即推送"
   - 验证点：改城市后点预览，返回的图片中城市名已变；此时 `/wallpaper/info` 的 `length` 未变（证明预览确实没推送）
3. APScheduler 按配置周期轮换推送
   - 验证点：把周期临时设为 2 分钟，观察日志连续两轮推送了不同页面
4. 服务绑定 `0.0.0.0` 以便手机访问，并在 README 记录访问地址
   - 验证点：手机浏览器能打开配置页

**若失败**：调度器不要吞异常，单页渲染失败应跳过该页继续轮换，并把异常写入日志。

## Phase 4 — 行情页与新闻页

两者与天气同构，可并行开发。

**步骤**

1. `providers/stocks.py`：按配置的代码清单抓行情。股票清单是 `config.json` 里的普通字段，**用户随时可以在 Web 界面里增删**，不要把清单硬编码进代码逻辑本身（清单值本身可以有默认值）。用户确认的初始清单（2026-07-28）：**苹果（AAPL）、英伟达（NVDA）**，写入 `config.example.json` 的默认值
   - 验证点：给定 2–3 个代码，返回含名称、现价、涨跌幅的列表
2. `renderer/stocks.py`：标题 + 最多 5 行数据 + 可选走势线。超过 5 条时分页轮换
   - 验证点：负载 < 5000（实测同版式 3236）；涨跌幅用纯黑而非灰色（灰度 85 对比度不足）
3. `providers/news.py`：公开 RSS 源（新浪滚动新闻等），源地址可配置
   - 验证点：返回至少 5 条标题
4. `renderer/news.py`：标题 + 最多 8 行文字，按字宽截断
   - 验证点：负载 < 6000（实测同版式 4440）；中英文混排不溢出画布

## Phase 5 — Claude Code 用量页

**步骤**

1. `providers/ccusage.py`：解析 `$CLAUDE_CONFIG_DIR/projects/**/*.jsonl`（`CLAUDE_CONFIG_DIR` 未设时回落 `~/.claude`）
   - **必须按 `(message.id, requestId)` 去重**（实测存在重复记录）
   - **必须增量解析**：按文件 mtime + 已读偏移缓存，229MB 全量扫描不能每周期跑
   - 输出：今日 token 总量、最近 5 小时滚动窗口 token、按模型拆分、等价 API 成本
   - 验证点：`python3 -c "from providers.ccusage import summarize; print(summarize())"` 输出的今日 token 数量级合理；第二次调用耗时显著低于第一次（证明增量缓存生效）
2. `renderer/usage.py`：渲染用量页
   - **文案必须写明这是 token 消耗/等价成本，不是订阅额度百分比**（如标题写"Token 消耗"而非"用量额度"）
   - 验证点：目视确认无任何"剩余额度""已用 x%"之类会被误读为官方口径的表述

**若失败**：若解析出的数字与 `ccusage` 工具（`npx ccusage@latest`，本机 npx 可用）差异过大，以后者为参照排查去重逻辑。

## Phase 6 — 六爻起卦

**先读 ARCHITECTURE.md §4.3**，其中说明了设备无法作为输入设备这一硬约束。

**步骤**

1. `providers/liuyao.py`：纯计算模块，三枚铜钱抛六次
   - **用 `secrets` 而非 `random`**
   - 输出：六爻（老阴/少阳/少阴/老阳）、本卦、变卦、动爻位置
   - 可复用 `~/.agents/skills/mingli/scripts/meihua_engine.py` 的 `HEXAGRAM_NAMES` / `NUM_BA_GUA` / `GUA_WUXING` 三张静态表，**不要复用其生克逻辑**
   - 验证点：起卦 10000 次，六爻各爻的老阴/少阳/少阴/老阳分布接近 1:3:3:1（三钱法的理论分布）
2. Web UI 增加"摇卦"按钮，服务端起卦后渲染推送
   - 验证点：点击后设备显示卦象
3. `renderer/divination.py`：六爻爻象（阳爻实线、阴爻断线，动爻加标记）+ 本卦名 + 变卦名 + 一句短判断
   - 一屏只放得下这些，**不要试图放完整爻辞**
   - 验证点：`COMPRESS_RENDER` 中六条爻线清晰可辨，阴阳可区分
4. 实现"钉住"：卦象推送后暂停轮换 N 分钟（可配置，默认 30）
   - 验证点：把轮换周期设为 2 分钟、钉住设为 5 分钟，摇卦后观察 5 分钟内未发生轮换推送
5. 补全 64 卦的短判断文案（`meihua_engine.py` 仅覆盖约 10 卦）
   - 验证点：随机起卦 20 次，均有非兜底文案

**可选增强（非必需，不要因它阻塞交付）**：手机 DeviceMotion 摇一摇触发。**iOS 13+ 要求安全上下文**，局域网 HTTP 页在 iPhone Safari 上会失败，需自签 HTTPS 证书。按钮方案必须始终可用。

## 范围边界（本期明确不做）

- 不逆向 `COMPRESS_ARRAY_V2` 编码格式，不脱离厂商云端
- 不做六爻的纳甲、六亲、世应、六神装卦
- 不做 launchd 开机自启（先手动运行，稳定后再议）
- 不做多设备支持
- 不改设备固件，不碰任何需要拆机的方案

## 完成定义

全部 Phase 的验证点通过，且完成声明中必须包含以下**真实输出**（不接受"应该没问题"）：

1. Phase 0 的物理观测记录（刷新延迟秒数 + 1 小时持久性结论）
