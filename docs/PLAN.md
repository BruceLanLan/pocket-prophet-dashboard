# 开发计划（T6 规划交接单）

> **执行模型请先读完 `docs/ARCHITECTURE.md`**，本文档中所有"已确认事实"均在该文档中有实测依据，不重复展开。
>
> 本计划按**风险与信息增益排序**，不按功能重要性排序。不要重排阶段顺序。

---

## 目标

在 Mac 上运行一个常驻服务，用户在浏览器上触发，即时把内容渲染成 200×200 图像推送到"口袋先知"墨水屏设备。**五个页面都要做**：天气、股票行情、重大新闻、六爻卦象、Claude Code token 消耗（用户 2026-07-29 确认要这一整组）。所有数据源（城市、股票清单、新闻源）可在 Web 界面自定义。

**关于 Phase 0 与这五页的关系**：Phase 0 验证的是"推上去的图到底显不显示、显示多久"。它**不是用来砍页面的闸门**，而是用来确定这些页面的**实际体验等级**——只有在"完全不显示"这一种极端结果下才需要全面停工（见 Phase 0 三分支）。

**可验收的最终状态**：用户在设备上打开"更换壁纸"界面后，从浏览器点一下就能把任意一页（卦象 / 天气 / 行情 / 新闻 / 用量）推上设备并正确显示；设备不可达时，界面给出可操作的提示而非裸的连接错误。

**开发策略：离线优先。** 本项目绝大部分代码不需要设备在线就能开发和验证——云端 convert API 返回的 `COMPRESS_RENDER` 就是设备实际显示效果的 PNG 预览，可以用它验证每个页面的排版和可读性，全程不碰设备。**只有两件事需要设备**：Phase 0 的显示语义验证、以及每个功能最后"推真机确认"。因此执行顺序上**先把渲染管线和五个页面全部做出来、用预览验证到满意，再集中做需要设备的那几步**，尽量减少对用户配合设备的打断。

**用户已确认的优先级（2026-07-29）**：先做"信息显示"（天气/股票/新闻/卦象/用量），而非"蓝牙遥控器"扩展（后者记录在 `docs/OPTIONS.md` 文末，本期不做）。

## 约束（不可违反）

1. **设备不常驻联网**。它只在用户手动停留于"更换壁纸"界面时才可达（ARCHITECTURE.md §1.5，两份实测日志在 `docs/evidence/`）。**不要写调度器，不要设计任何形式的后台定时推送**——不存在可供调度的窗口。
2. **`POST /wallpaper` 不可逆**。没有读回接口，`DELETE` 恢复的是出厂内建壁纸而非用户上一张图。每次写入前必须先把源图存进 `history/`。
3. **设备是只写通道**。不要设计任何依赖"从设备读取状态/事件"的功能——接口不存在（已逐一探测确认）。
4. **按需渲染，不做预取缓存**。设备窗口由用户开启且较长，几秒延迟无感；预渲染是在为一个可能一天才出现一次的设备白烧厂商 API 配额。
5. **不要把 token 消耗标注为"额度"**。订阅额度百分比本地拿不到，见 ARCHITECTURE.md §4.2。
6. **不要复用 `meihua_engine.py` 的生克判断逻辑**（有 bug，见 ARCHITECTURE.md §4.3），静态数据表可以复用。
7. **不要在本期做纳甲装卦**，也不要启动 `COMPRESS_ARRAY_V2` 编码器逆向，二者均在范围外。
8. **不要做"设备出现即自动推送"的探测器**（理由见 ARCHITECTURE.md §3.1 末尾：设备出现的那一刻恰恰可能是用户想用官方页面传自己的图，自动推送会覆盖用户的操作）。
9. 设备 IP 必须是配置项，不允许硬编码 `192.168.3.235`。

## Phase 0 — 显示语义验证（阻断性，决定所有页面的实际体验等级）

**这是整个项目信息增益最高的一步，且是唯一需要付出不可逆代价的步骤（一张壁纸）。**

> **用户已同意覆盖当前壁纸**（2026-07-28 原话："背景图无所谓，我随时可以改"）。执行模型**不需要**再为这次覆盖征求同意，可直接执行。

已知"能把数据写进设备"，但**没有任何证据表明写进去的壁纸就是设备日常显示的画面**。四个待答问题：

- 设备**停留在"更换壁纸"界面时**，屏幕显示的是壁纸内容，还是二维码/配置提示？（决定"停驻模式"是否成立，见步骤 4）
- 推送的图是否成为设备待机时的常显画面？
- 设备原生内容（每日运势、答案之书等）是否会覆盖它？
- 设备离网后面板还刷新吗？

**这四个答案决定五个页面的实际体验等级**，并在极端情况（完全不显示）下决定是否全面停工。四个问题在同一次观察里就能全部回答。

**步骤**

1. 请用户在设备上打开"更换壁纸"界面，使设备联网
   - 验证点：`curl -s -m 5 --noproxy '*' http://<设备IP>/wallpaper/info` 返回含 `has_custom` 的 JSON。记录 `length` 原值
2. 生成一张高辨识度测试图（200×200，含大号时间戳文字 + 四级灰阶色块 + 四角定位标记），走云端转换
   - 验证点：`COMPRESS_ARRAY_V2` 长度 < `max_upload`；解码 `COMPRESS_RENDER` 目视确认排版正确
3. `POST /wallpaper` 写入
   - 验证点：HTTP 200，且再查 `/wallpaper/info` 时 `length` 已变为新值
4. **推送完成、用户仍停留在该界面时**，先问一个同等重要的问题（成本为零，一并观察即可）：
   - **此刻屏幕上显示的是什么？** 是壁纸本身（或刚推上去的图），还是二维码/配置提示之类的界面？
   - 这个问题决定"停驻模式"是否成立：探测 A 已证明设备停在该界面可连续在线一小时以上，**若停驻时屏幕显示的就是壁纸内容，那么仪表盘可以做成真正的定时刷新**（代价是耗电），仪表盘功能不必依赖"离网后留存"这一条也能活
5. **请用户退出"更换壁纸"界面**，然后在三个时间点肉眼观察设备屏幕并回报（这一步只能由人做，执行模型必须停下来等用户回报，不得自行推断）：
   - **立即**：屏幕上是不是我们推的那张测试图？
   - **约 10 分钟后**：还在吗？有没有被设备原生画面替换？
   - **约 1 小时后**：还在吗？
   - 另外记录：从 POST 到画面实际变化经过了多久
6. 把观测结果写入 `docs/PHASE0_FINDINGS.md`，并据此更新 ARCHITECTURE.md §4 开头的判定

**分支（三种结果，必须按实测结果走，不得跳过判断）**

注意这里是**三分支不是二分支**：图"不持久"和图"根本不显示"是完全不同的两回事，后者会连摇卦一起废掉（卦象走的是同一个接口、同一块屏幕）。

- **结果 A — 持久显示**（测试图成为待机常显画面并稳定留存）：**五个页面全做**，仪表盘具备"每天开一次界面、全天显示当日信息"的环境价值。这是最好的结果。
- **结果 B — 仅短暂显示**（推送后能看到，但离网后被设备原生画面覆盖）：**五个页面仍然全做**，但仪表盘退化为"开界面时看一眼即走"，环境价值消失、实用价值下降。摇卦**不受影响**（本来就是推完立刻看）。**不要因为结果 B 就砍页面**——用户已明确表示要这五页，是否保留由用户决定，执行模型只负责如实报告体验差异。
- **结果 C — 完全不显示**（壁纸根本不是屏幕显示的内容）：**整个项目的显示前提不成立，五个页面全部停工**。这种情况下摇卦同样无法交付，不存在"收敛为摇卦"这个退路。**立即停止并向用户报告**，此时可选的方向只剩 `docs/OPTIONS.md` 文末的蓝牙遥控器扩展（它不依赖屏幕显示）。

## Phase 1 — 推送管线骨架

打通"渲染 → 转换 → 推送"最小闭环。这套管线摇卦和仪表盘都要用，无论 Phase 0 结果如何都必须做。

**步骤**

1. 实现 `device.py`：
   - `info(ip) -> dict | None`：探活 + 读状态，不可达时返回 `None` 而非抛异常
   - `convert(img: PIL.Image, kernel: str = "THRESHOLD") -> str`：调云端，返回 base64 负载
   - `push(payload: str, ip: str)`：写设备
   - 内置：推送前探活、负载超限拒绝、内容哈希去重、源图存入 `history/YYYYMMDD-HHMMSS.png`、云端失败指数退避
   - 验证点：对一张纯白图调 `convert`，返回长度在 40–200 之间（实测纯色图为 44–96 字符）
   - 验证点：设备离线时调 `push`，在 8 秒内返回明确的"设备不可达"结果，且不抛裸异常
2. **设备不可达是常态，不是异常**。所有对外提示必须可操作，统一文案示例："设备当前不在线，请先在设备上打开'更换壁纸'界面"
   - 验证点：设备离线时从 Web 界面点推送，页面显示上述提示而非 500 错误页或连接超时堆栈
3. **IP 漂移自愈**：设备无 mDNS 主机名、无反向 DNS（已实测），唯一稳定标识是 MAC（本机为 `58:2a:bd:0a:98:c8`，随硬件不同）。配置同时存 `device_ip` 与 `device_mac`；探活失败时执行 `arp -a`，找 MAC 匹配行解析出新 IP，更新配置后重试一次
   - 验证点：手动把配置里的 IP 改错，在设备在线时触发推送，日志显示"IP 已更新"并推送成功
4. 实现 `renderer/base.py`：画布常量（200×200）、四级灰阶调色板 `{0,85,170,255}`、字体加载（`/System/Library/Fonts/STHeiti Medium.ttc`）、按字宽截断、分隔线等原语
   - 验证点：绘制含 13px 中文的测试图，解码 `COMPRESS_RENDER` 后目视可读

## Phase 2 — 六爻起卦

**为什么它排在其他四页之前**（是构建顺序的考量，不是重要性排序——五页同等要做）：

1. **它是唯一不依赖外部数据源的页面**，数据完全由本地计算产生。不用等接入天气/行情/新闻 API，就能最快跑通"渲染 → 转换 → 预览"全链路，尽早验证管线是否正确。
2. **它也是唯一不受 §1.5 联网约束削弱的页面**——摇卦本就是推完立刻看的一次性动作，Phase 0 无论出结果 A 还是 B，它的体验都不打折。

因此把它当作管线的"第一个真实用例"最省事，风险也最低。

**先读 ARCHITECTURE.md §4.3**，其中说明了设备无法作为输入设备这一硬约束：无法读取摇动，起卦只能由 Web 界面触发，设备负责显示。

**步骤**

1. `providers/liuyao.py`：纯计算模块，三枚铜钱抛六次
   - **用 `secrets` 而非 `random`**
   - 输出：六爻（老阴/少阳/少阴/老阳）、本卦、变卦、动爻位置
   - 可复用 `~/.agents/skills/mingli/scripts/meihua_engine.py` 的 `HEXAGRAM_NAMES`、`NUM_BA_GUA`、`GUA_WUXING`、`GUA_READING` 四张静态表（`GUA_READING` 完整覆盖 64 卦，可直接当短判断文案用，见步骤 5）；**不要复用其生克逻辑**（该处两个分支条件写成了等价表达式，第二支永远不可达）
   - 验证点：起卦 10000 次，各爻的老阴/少阳/少阴/老阳分布接近 1:3:3:1（三钱法理论分布），打印实际统计
2. 最小 Web 服务（Flask 或 FastAPI）：一个页面、一个"摇卦"按钮、一个设备在线状态指示
   - 绑定 `0.0.0.0` 以便手机访问
   - 验证点：手机浏览器能打开页面并看到设备在线/离线状态
3. `renderer/divination.py`：六爻爻象（阳爻实线、阴爻断线、动爻加标记）+ 本卦名 + 变卦名 + 一句短判断
   - 一屏只放得下这些，**不要试图放完整爻辞**
   - 验证点：`COMPRESS_RENDER` 中六条爻线清晰可辨，阴阳可区分
4. 串起来推真机
   - 验证点：设备在线时点"摇卦"，设备显示卦象，与 `COMPRESS_RENDER` 一致
5. 短判断文案直接复用 `meihua_engine.py` 的 `GUA_READING`（完整覆盖 64 卦，逐条核对过，不是之前记的"仅约 10 卦"，那是读文件时看漏的）。**不需要另写文案**，只需按本卦的卦名去查表
   - 验证点：随机起卦 20 次，均能查到非空文案

**可选增强（不要因它阻塞交付）**：手机 DeviceMotion 摇一摇触发。**iOS 13+ 要求 `requestPermission()` 且必须在安全上下文中调用，局域网 HTTP 页在 iPhone Safari 上会失败**，需自签 HTTPS 证书。按钮方案必须始终可用。

## Phase 3 — 配置界面

**步骤**

1. `config.json` schema + `config.example.json`：设备 IP、设备 MAC、启用的页面、天气城市（默认深圳）、股票清单（默认 `AAPL`、`NVDA`，用户 2026-07-28 确认）、新闻源列表

## Phase 4 — 天气 / 行情 / 新闻页

> Phase 0 出现**结果 C（完全不显示）**时停工；结果 A 或 B 都照常做。结果 B 下这几页的实用价值会下降，但保留与否由用户决定，不要自行砍掉。

天气、行情、新闻三者同构，共用 `fetch() -> dict` 接口，差异只在渲染。数据在用户触发推送时即时抓取，不预取。

1. `providers/weather.py`：城市可配置，选无需 API key 的公开源（如 wttr.in），源地址写进配置以便替换
   - 验证点：`python3 -c "from providers.weather import fetch; print(fetch('深圳'))"` 输出含温度、天气描述、湿度的 dict
2. `renderer/weather.py`：城市 22px、温度 52px、描述 18px、湿度风力 14px 灰、分隔线、明后两日 13px 灰、更新时间 11px 灰
   - 验证点：负载 < 5000（实测同版式 2792）
3. `providers/stocks.py` + `renderer/stocks.py`：标题 + 最多 5 行数据 + 可选走势线，超 5 条分页
   - 验证点：负载 < 5000（实测同版式 3236）；**涨跌幅用纯黑 `0` 而非灰 `85`**（灰度对比度不足）
4. `providers/news.py` + `renderer/news.py`：公开 RSS（新浪滚动新闻等），源可配置；标题 + 最多 8 行，按字宽截断
   - 验证点：返回至少 5 条标题；负载 < 6000（实测同版式 4440）；中英文混排不溢出画布

## Phase 5 — Claude Code token 消耗页

1. `providers/ccusage.py`：解析 `$CLAUDE_CONFIG_DIR/projects/**/*.jsonl`（`CLAUDE_CONFIG_DIR` 未设时回落 `~/.claude`；本机实测为 `/Users/bruce/.claude-opus`，365 个文件、229MB）
   - **必须按 `(message.id, requestId)` 去重**（实测存在同一消息重复写入，两条记录 token 完全相同）
   - **必须增量解析**：按文件 mtime + 已读偏移缓存，229MB 全量扫描不能每次推送都跑
   - 输出：今日 token 总量、最近 5 小时滚动窗口 token、按模型拆分、等价 API 成本
   - 验证点：`python3 -c "from providers.ccusage import summarize; print(summarize())"` 输出数量级合理；第二次调用耗时显著低于第一次（证明增量缓存生效）
   - 若数字与 `npx ccusage@latest`（本机 npx 可用）差异过大，以后者为参照排查去重
2. `renderer/usage.py`
   - **文案必须写明是 token 消耗/等价成本，不是订阅额度百分比**（标题用"Token 消耗"而非"用量额度"）
   - 验证点：目视确认无"剩余额度""已用 x%"之类会被误读为官方口径的表述
