## 1. 硬件与接口事实（已实测确认）

### 1.1 设备形态

"口袋先知"是一块墨水屏小设备，配网后以普通设备身份接入你的局域网，并在 **80 端口**提供一个极简 HTTP 服务。所有未知路径都会 302 跳转到 `http://192.168.4.1/`（这是 ESP32 系列 SoftAP 的经典地址），说明固件是 captive-portal 风格的配置服务。

本项目开发机实测设备地址为 `192.168.3.235`，**该地址由路由器 DHCP 分配，会变**。生产实现必须把地址做成配置项，并建议在路由器上为设备 MAC 绑定静态 IP。

### 1.2 完整接口清单

设备暴露的接口**只有以下四个**。这是通过对 23 个常见路径（`/api` `/status` `/device` `/config` `/battery` `/sensor` `/event` `/shake` `/button` `/nfc` `/display` `/ota` `/debug` `/metrics` `/health` 等）逐一探测确认的——全部返回 302 跳转，无一命中。

| 方法 | 路径 | 语义 |
|---|---|---|
| GET | `/` | 官方"更换壁纸"网页（HTML + 内联 JS） |
| GET | `/wallpaper/info` | 返回 `{has_custom, length, capacity, max_upload}` |
| POST | `/wallpaper` | 写入壁纸。body 为 `COMPRESS_ARRAY_V2` 的 base64 **字符串原文**，`Content-Type: application/octet-stream` |
| DELETE | `/wallpaper` | 恢复出厂内建壁纸 |

`GET /wallpaper/info` 的实测返回：

```json
{"has_custom":true,"length":12160,"capacity":16352,"max_upload":14336}
```

**单位是 base64 字符数，不是解码后的字节数。** 依据：官方网页的 JS 中 `uploadConverted(text)` 用 `text.length > maxUpload` 做校验，而 `text` 是 `String(j.COMPRESS_ARRAY_V2)` 这个 base64 字符串本身，随后原样 POST。

### 1.3 由接口清单推出的三条硬约束

这三条决定了整个系统的形态，必须在设计中始终遵守：

1. **WiFi 通道是单向只写的。** HTTP 接口读不到任何设备状态：拿不到电量、拿不到按键事件、拿不到当前显示内容。设备在这条通道上只能被"推"，不能被"问"。
   > **重要修正**：这条曾被写成"设备是纯只写的、无法作为输入设备"，**该表述已被推翻**。设备通过**蓝牙 HID** 存在一条独立的"设备 → 主机"输入通道，详见 §1.6。本条的适用范围仅限 WiFi/HTTP 通道。
2. **写入不可逆。** 没有读回接口，`DELETE` 恢复的是**出厂内建壁纸**而非用户上一张自定义图。覆盖前必须自行保留源图。
3. **每次渲染都依赖厂商云端。** 设备只认识 `COMPRESS_ARRAY_V2` 这种私有编码，而编码只能由厂商云端 API 产出（见 2.1）。这是整条链路上的单点故障。

### 1.4 面板规格（实测确认）

- 分辨率 **200×200**
- **4 级灰阶**，实测灰度值为 `{0, 85, 170, 255}`

确认方式：把云端 API 返回的 `COMPRESS_RENDER`（base64 PNG 预览）解码后直接量取尺寸与像素值，非推算。

> 早期曾按 240×240 推测并据此做过一批单像素标记实验，该批实验**已作废**：云端会把输入图缩放到 200×200，(0,0) 处的单像素黑点缩放后变成灰色 `(85,85,85)`，标记实验的前提不成立。所有测试图必须按原生 200×200 出图。

### 1.5 设备联网时机 —— 本项目最重要的约束

**设备不常驻联网。它只在用户手动停留在"更换壁纸"界面期间才加入局域网。**

结论来自两次探测的对照，两份原始日志都在 `docs/evidence/` 下。**两者的差异本身才是证据**，单看任何一份都会得出错误结论。

**探测 A（`poll-A-while-page-open.log`）**：5 分钟间隔轮询 `/wallpaper/info` 共 13 次、覆盖 60 分钟，13/13 全部成功。据此一度得出"HTTP 服务常驻、不会空闲关闭"的结论。

**该结论是错的。** 这一小时里用户始终停留在设备的"更换壁纸"界面上，测的是"停留在该界面期间"的可用性，而非设备的常态可用性。测试设计本身没有区分这两者。

**探测 B（`poll-B-after-exiting-page.log`）**：用户手动退出该界面后立即复测，随后每 60 秒轮询一次 ping + HTTP，共 25 次、覆盖 25 分钟：

```
20:39:17  curl /wallpaper/info → HTTP 000（5 秒超时）
          ping 192.168.3.235   → 3/3 100% 丢包
          arp -a 仍有旧记录     → 仅 ARP 缓存未过期，不代表设备在线

20:40–21:05  25 次采样，25/25 全部 ping_rc=2 + http=000
```

设备在网络层（ICMP）与应用层（HTTP）**同时立即不可达**，且 25 分钟内从未自行出现。

**这条结论的边界**（不要过度解读）：

- 探测 B 的采样粒度是 60 秒。若设备存在**极短的周期性唤醒窗口**（例如每 30 分钟醒 10 秒），这个密度大概率会错过。严格说，本测试排除的是"存在可被工程利用的常规唤醒窗口"，而非"绝对不存在任何唤醒"。但这不改变决策：一个如此短暂、起点又无法预测的窗口，同样不可依赖。
- 只测了"退出更换壁纸界面"这一种设备状态。**未测试**：充电时、开机瞬间、停留在其他菜单界面、NFC 触碰时是否会联网。若日后发现其他状态也联网，本节需更新。

**对架构的影响**：不存在任何可以被动等待的推送窗口。"常驻服务按周期自动推送"这一形态不成立，架构改为**用户触发式**，详见 §3。这条约束对五个功能的杀伤力**并不均等**，见 §4 各节。

**补充发现（2026-07-29，Phase 2 端到端真机验证时观察到）**：成功 `POST /wallpaper` 之后，设备很快自行离线——`curl`/`ping` 均超时。这与官方网页的前端逻辑吻合：`save()` 成功后执行 `window.location.replace('about:blank')`，即"保存成功即退出配置页"。也就是说触发离线的不只是"用户手动退出界面"，**一次成功的写入本身也会结束这次连通窗口**。对使用侧的影响：每次推送都是"一次性"的——推完这一次，下一次推送前必须让用户重新打开一次"更换壁纸"界面，不能假设窗口会持续到下一次操作。`app.py` 的状态轮询已经能正确反映这一点（推送后再查询会显示离线），不需要额外处理，但这里记一笔供后续踩坑时对照。

### 1.6 蓝牙 HID 通道（实测确认存在，是一条独立的输入通道）

设备以 **`Rand/0 Pager`** 的名字广播 BLE，可被 macOS 直接配对连接。`Rand` 与云端 API 的 `series: "rand"` / `model: "rand_0"` 完全对应，确认是同一产品线。

**硬件身份确认**：

- BLE 地址 `58:2A:BD:0A:98:CA`，WiFi 地址 `58:2A:BD:0A:98:C8`，**相差 2**。这是 ESP32 的标准 MAC 分配规律（WiFi STA = 基址，蓝牙 = 基址 + 2），确认两个接口属于同一颗芯片。
- HID 属性中 `ModelNumber = "NimBLE"`，NimBLE 是 ESP32 上最常用的蓝牙协议栈。

**设备在系统中的身份**：`Minor Type: Keyboard`，`Transport: Bluetooth Low Energy`，即一个标准 BLE HID 键盘。**它能向 Mac 发送按键事件**——这正是本项目此前认定"不存在"的输入通道。

**HID 报告描述符解码**（原始值见 `ioreg -c IOHIDDevice`，共 113 字节），设备声明了三组能力：

| 集合 | Usage Page | Report ID | 内容 |
|---|---|---|---|
| 1 | Generic Desktop / Keyboard | 1 | 标准键盘：8 位修饰键 + 6 键码。**含 LED 输出**，说明主机→设备方向的报告通道也存在 |
| 2 | Consumer (0x0C) | 2 | 多媒体控制键，16 位 |
| 3 | **厂商自定义 (0xFF00)** | 3 | **1 字节私有输入通道**，取值 0–255 |

第三组是最有价值的发现：厂商自定义 Usage Page 意味着设备有一条**私有数据通道**可以向主机发送任意字节值，而不只是模拟键盘按键。这条通道具体传什么、由什么动作触发（按键？摇动？）尚未测定。

另外 `MaxOutputReportSize = 2`、`MaxFeatureReportSize = 1`，说明主机→设备方向也有小容量的报告通道，但描述符里只声明了标准键盘 LED 用途，能否承载自定义数据未知。

**蓝牙同样是模式门控的，不存在常驻通道（已实测定论）**：

用户手动退出蓝牙翻页模式后立即检测：

```
00:54:41  已连接列表中：0（消失）
          未连接列表中：1（掉入此列）
          HID 设备树条目：3 → 0（彻底从系统移除）
```

**结论：BLE 与 WiFi 的行为完全一致——只在用户手动进入对应界面时开启，退出即断开。** 设备上不存在任何常驻的对外通道。

> **一个方法论记录**：在此之前曾做过一次 3 分钟、36 次采样的连接监测，全程显示"保持连接"。但那次测试期间用户仍停留在翻页模式，因此该数据**无法区分"常驻"与"停留期间可用"**，与 §1.5 中 WiFi 探测 A 的错误完全同源。当时未据此下结论是正确的。**设计验证实验前必须先问：这个测试能否区分我要区分的两种情况？**

**由此推出的进一步结论**：

- 两条通道**几乎必然互斥**——设备 UI 一次只能停在一个界面，而两条通道各自绑定一个界面。
- 因此"按设备按键 → Mac 收到 → 起卦 → 推回设备显示"的完整闭环**不成立**：无法同时处于发信号的翻页模式和收推送的壁纸模式。
- **蓝牙通道对"信息显示"这个目标没有带来可用的增量**。理论上还剩一个"排队"模型（翻页模式按键起卦 → 暂存 → 下次进壁纸界面时推送），但它要求用户依次进入两个模式，步骤比"直接进壁纸界面、网页点一下"更多，UX 更差，不采用。
- 但蓝牙 HID 本身仍是一个**范围内的独立扩展方向**：把翻页键当作 Mac 的实体遥控器（重映射成任意快捷键或脚本触发器）。它不依赖屏幕显示，与信息显示互不干扰。本期不做，记录在 `docs/OPTIONS.md` 文末。

**这次探索仍有两项持久价值**：

1. **确认了 ESP32 + NimBLE**，为固件路线提供了确定的技术前提。
2. **发现了厂商自定义 HID 通道的存在**，说明固件里有私有协议——这是固件分析时的已知靶点。

另外可以确定的是：既然 WiFi/BLE 的开关策略是**固件策略**而非硬件限制（ESP32 硬件支持二者共存与常驻），那么能解除"模式门控"这一根本约束的路径**只有改固件**。

> **但改固件已明确划在本项目范围之外**（见 README「定位：扩展，不是破解」）。这里记录该判断，只是为了说明"模式门控"这个约束在当前范围内**无解、只能接受并绕过**，而不是把固件列为待办。

## 2. 厂商云端转换接口

### 2.1 请求契约

```
POST https://dot.mindreset.tech/api/authV2/device/render/convert
Content-Type: application/json

{
  "series": "rand",
  "model": "rand_0",
  "edition": 1,
  "image": "data:image/png;base64,....",
  "colorLevels": 4,
  "ditherType": "DIFFUSION",
  "ditherKernel": "THRESHOLD"
}
```

`ditherKernel` 的十个合法值（照抄官方网页下拉选项）：

`FLOYD_STEINBERG` `THRESHOLD` `ATKINSON` `SIERRA2` `BURKES` `STUCKI` `JARVIS_JUDICE_NINKE` `DIFFUSION_ROW` `DIFFUSION_COLUMN` `DIFFUSION_2D`

返回：

```json
{
  "COMPRESS_ARRAY_V2": "设备专用编码，base64 字符串，原样 POST 给设备",
  "COMPRESS_RENDER": "base64 PNG，设备端真实渲染效果，仅供预览"
}
```

`COMPRESS_RENDER` 在开发期非常有用：它就是设备实际会显示的画面，可以在不写入设备的前提下验证排版和可读性。

### 2.2 负载预算（实测数据）

上限 14336 base64 字符。用四张仿真图 × 两种抖动核实测：

| 图像类型 | THRESHOLD | FLOYD_STEINBERG |
|---|---|---|
| 天气页（大字 + 少量文字） | 2792 (19%) | 4120 (28%) |
| 行情页（5 行数据 + 走势线） | 3236 (22%) | 4824 (33%) |
| 新闻页（8 行密集文字） | 4440 (30%) | 5632 (39%) |
| 全屏渐变（最坏情况，照片类） | 2412 (16%) | 9716 (67%) |

**结论：扁平化图文设计远在预算内，负载不构成约束。** 两条设计指令由此确定：

- **默认用 `THRESHOLD`**，它比 `FLOYD_STEINBERG` 省约 30%，且扁平设计本就没有需要抖动的渐变。
- **避免照片和大面积渐变**。渐变图在抖动下能吃掉 67% 预算，是唯一接近上限的情况。

### 2.3 可读性实测

对新闻页与行情页解码 `COMPRESS_RENDER` 后目视验证（字体 `/System/Library/Fonts/STHeiti Medium.ttc`）：

- **13px 中文可读，14px 舒适。13px 是下限，不要更小。**
- 13–14px 下每行约容纳 **14 个汉字**
- 一屏可容纳"标题 + 5 行数据 + 一条走势线"或"标题 + 8 行文字"
- 1px 线条渲染干净，可用于分隔线与走势图
- 灰度 `85` 可用于次要信息，但对比度明显下降；**关键数字一律用纯黑 `0`**

## 3. 系统架构

### 3.1 形态选择：用户触发式，不是定时推送

受 §1.5 约束，设备只在用户主动打开"更换壁纸"界面时才可达。因此**没有调度器**——不存在可供调度的时间窗口。

真实的交互时序是：

```
用户在设备上打开"更换壁纸"界面
        ↓  设备加入局域网，80 端口可达
用户在手机/电脑浏览器打开本服务的 Web 界面
        ↓  点"摇卦"或"推送某页"
服务即时抓数据 → 渲染 200×200 → 调云端转换 → POST /wallpaper
        ↓
用户退出界面，设备离网（推送内容是否留在屏幕上 = Phase 0 待验证）
```

关键推论：**渲染必须按需即时进行，不要预渲染缓存**。设备的可达窗口由用户开启且持续时间较长（探测 A 显示可达一小时以上），几秒的抓取加转换延迟完全无感；而预渲染是在为一个可能一天才出现一次的设备反复消耗厂商 API 配额。

```
┌──────────────────────────────────────────────────┐
│  Mac 上的常驻服务 (FastAPI/Flask，无调度器)         │
│                                                  │
│  Web UI ─────────────┐                           │
│  (配置/预览/摇卦/推送) │  ← 用户触发是唯一入口       │
│                      ▼                           │
│  providers/     ─→ renderer/  ─→ device.py       │
│   weather.py       PIL 绘制     ├ 调云端 convert  │
│   stocks.py        200×200      ├ 负载校验        │
│   news.py          4 级灰阶      └ POST /wallpaper │
│   ccusage.py                                     │
│   liuyao.py                                      │
└──────────────────────────────────────────────────┘
                          │
                          ├──→ dot.mindreset.tech (转换)
                          └──→ 192.168.x.x (设备，仅窗口期可达)
```

服务本身仍需常驻，理由是它要随时能接住用户触发（用户不会为了推一张图先去启动一个进程），而不是因为它要定时干活。

**关于"设备出现即自动推送"的探测器**：技术上可以每几秒扫一次局域网，发现设备就自动推最新内容。**本期不做**，主要理由是它与官方上传流程直接冲突——设备出现的那一刻，恰恰可能是用户想用官方页面传自己的图，此时自动推送会把用户的操作覆盖掉。若日后确实需要，必须默认关闭、由用户显式"布防"。

### 3.3 推送管线的状态规则

这几条不是优化项，是正确性要求：

1. **推送前校验负载**：`len(payload) > max_upload` 时拒绝推送并告警，不要指望设备返回可读错误。
2. **推送前先探活**：设备大部分时间不可达（§1.5）。推送前先 `GET /wallpaper/info` 确认在线；不可达时给出明确提示"请先在设备上打开'更换壁纸'界面"，而不是抛一个裸的连接超时。这是本项目最高频的失败路径，错误信息必须可操作。
3. **内容未变则不推送**：对渲染出的 PNG 做哈希，与上次推送的哈希相同就跳过。墨水屏每次刷新都消耗电量并产生残影。
4. **保存每次推送的源图**：写入 `history/`，因为设备侧没有读回接口，这是唯一的回滚依据。
5. **云端失败要退避**：连续失败时指数退避并如实上报，不要静默重试。

> 早期版本曾要求"摇卦结果钉住 30 分钟以免被轮换冲掉"。**该机制已删除**：既然没有定时轮换，就没有任何东西会冲掉卦象，推上去的内容会一直留到下一次用户主动推送。

### 3.4 显示哪一页

原先设计的"按小时定时轮换"已随 §1.5 作废——没有调度器，也就没有轮换。

取而代之：**用户在 Web 界面上选择本次推送哪一页**，推上去就一直留着，直到下一次主动推送。这比自动轮换更简单，也更符合"一次交互推一次"的真实节奏。

若日后 Phase 0 证明仪表盘页面仍有价值、并补上了自动探测器（§3.1 末尾），可以让"每次设备出现时自动推下一页"作为一种可选模式，但那是后话。

## 4. 各功能模块的设计与约束

> **先读这段**：§1.5 的约束对五个功能的杀伤力**极不均等**，这决定了开发顺序（但不决定做不做——用户 2026-07-29 已确认五页全要）。
>
> **摇卦完好无损。** 它本来就是一个**有意为之**的动作：你拿起设备、想求一卦、触发、看结果。"需要动手"不是成本，那正是仪式本身，何况你手里已经握着这台设备了。
>
> **天气 / 行情 / 新闻 / 用量四页的价值被削弱。** 它们本来的价值在于**环境化**——瞥一眼就是最新的。现在每次刷新都要先在设备上翻进"更换壁纸"界面，这削掉了它们相当一部分意义。削弱到什么程度，取决于一个未验证的事实：推送的壁纸在设备离网后，是否作为待机画面**持续留在屏幕上**？
>
> - 若**持久留存** → "每天早上开一次界面，设备全天显示今日天气和行情"，环境价值大体保住。
> - 若**离网即被原生画面覆盖** → 退化为"开界面时看一眼即走"，实用价值明显下降。
>
> **但无论哪种，都不要自行砍页面。** 用户已明确要这五页，价值判断归用户。执行模型的职责是如实报告体验差异，而不是替用户做取舍。**唯一需要全面停工的情况是"推上去的图根本不显示"**——那时连摇卦也无法交付。三种结果的完整分支见 PLAN.md 的 Phase 0，**不要在实测前假设答案**。

### 4.1 天气 / 行情 / 新闻

数据源在配置中可改，这是用户的明确诉求。三者都属于"抓取 → 渲染 → 推送"的同构管线，实现上应共用同一套接口（`fetch() -> dict`），差异只在渲染。

渲染受 §2.3 的可读性约束：一屏 8 行文字或 5 行数据是上限，超出必须分页或截断。新闻标题必然需要截断，截断策略应按字宽而非字数计算（中英文混排）。

数据抓取一律在用户触发推送时即时进行（§3.1），不做预取缓存。

### 4.2 Claude Code 用量 —— 重要的范围澄清

**能做的**：本地转录文件完整可解析。路径 `~/.claude-opus/projects/**/*.jsonl`（注意：由 `CLAUDE_CONFIG_DIR` 环境变量决定，本机为 `/Users/bruce/.claude-opus`，**不是**默认的 `~/.claude`）。实测 365 个 jsonl、229MB。每条助手消息含：

```
message.usage.input_tokens
message.usage.output_tokens
message.usage.cache_creation_input_tokens
message.usage.cache_read_input_tokens
message.model          # 如 "claude-sonnet-4-5-20250929"
timestamp              # ISO8601，如 "2026-07-28T11:07:40.092Z"
requestId              # 如 "req_011CdUMCyEY2f6yE6hqy1UAc"
message.id             # 如 "msg_011CdUMD5EwUnSVkoybjVBKJ"
isSidechain            # 布尔，子 agent 流量标记
```

由此可算出：今日 token 消耗、滚动窗口内 token 总量、按模型拆分、等价 API 成本、趋势。

**不能做的**：`/usage` 命令显示的**订阅额度百分比拿不到**。已确认本地无任何缓存（检查了 `~/.claude-opus/.claude.json` 全部顶层键，无 quota/limit/rate 相关缓存；`cachedExtraUsageDisabledReason` 为 None）。该数据仅存在于服务端。

**因此**：本功能的交付物是"token 消耗与等价成本"，它**近似**但**不等于**官方额度百分比。UI 与渲染文案必须如实标注，否则用户会把结果当成官方口径而判定为错误数据。

**两个实现要点**：

- **必须去重**。实测样本中存在同一条消息重复写入（`11:07:40.092` 与 `11:07:41.412` 两条记录 token 完全相同）。去重键用 `(message.id, requestId)`，二者均已确认存在。
- **必须增量解析**。229MB 全量扫描不能每个渲染周期跑一次。按文件 mtime + 已读偏移量做缓存。

### 4.3 摇卦

> **关于蓝牙的补充（结论：不改变本节方案）**：设备确实能通过蓝牙 HID 向 Mac 发送按键事件，所以"设备无法作为输入设备"这句话严格来说只对 WiFi 通道成立。但实测确认蓝牙同样是模式门控的，且与 WiFi 模式互斥（§1.6），无法实现"按键触发 → 立即显示"的闭环。**因此下方的网页触发方案仍是唯一可用方案。**

**在 WiFi/HTTP 通道上**，§1.2 的接口探测已确认：没有任何接口可以读取摇动、按键或 NFC 事件。设备只能显示卦象、不能触发起卦。

两种触发方式：

1. **Web UI 按钮 + 服务端 CSPRNG（默认方案）**。用 `secrets` 模块而非 `random`，模拟三枚铜钱抛掷六次。可靠、无平台依赖。
2. **手机浏览器 DeviceMotion（增强方案，非必需）**。用户在手机上打开配置页摇晃手机，由浏览器读取加速度计驱动起卦，保留"摇"的仪式感。**注意 iOS 13+ 要求 `requestPermission()` 且必须在安全上下文中调用——局域网 HTTP 页面在 iPhone Safari 上会失败**，需要自签证书走 HTTPS。此方案有平台风险，**不允许作为默认路径**，只能作为可选增强。

> 早期版本还列了"定时自动起卦（每日一卦）"作为第三种方式。**该方案已删除**：受 §1.5 约束，设备平时不在网上，定时任务无处投递。

**为什么这个功能不受 §1.5 影响**：摇卦是一次**有意为之**的交互——用户想求一卦时，本来就要拿起设备、专注地看结果。"需要手动打开界面"在这里不是摩擦，而是仪式的一部分；而对天气、行情这类环境化信息，同样的手动步骤就抽掉了它们的全部意义。这是本项目开发顺序把摇卦排在仪表盘之前的根本原因。

**关于卦法与可复用资产**：

用户诉求是"六爻"（三枚铜钱抛六次，得本卦与变卦）。本机已有的 `~/.agents/skills/mingli/scripts/meihua_engine.py` 是**梅花易数**引擎，与六爻是不同体系，但其中的静态数据表可以复用：

- 可复用：`HEXAGRAM_NAMES`（64 卦完整上下卦组合表）、`BA_GUA_NUM`/`NUM_BA_GUA`（先天八卦数）、`GUA_WUXING`（八卦五行）、`GUA_READING`（64 卦一句式短判断，完整覆盖，见下方订正）
- **不要复用其生克判断逻辑**，该处有 bug：`'体克用' if low_wx == up_wx else ('用生体' if up_wx == low_wx else ...)` 中前两个条件表达式等价，第二分支永远不可达；且五行相同应为"比和"而非"体克用"。
- `HEXAGRAM_DEEP`（约 10 卦）不够用，但 `GUA_READING` 完整覆盖全部 64 卦（逐条核对过，一句式判断，如"乾为天：元亨利贞——强健不息，事在人为"），**可直接复用作为一屏短判断的文案，不需要补全**。之前记成"只覆盖约 10 卦"是读文件时看漏的，已订正。

六爻的**起卦**部分（三钱六掷 → 六爻 → 本卦/变卦）逻辑简单，几十行即可写全，应新写。真正昂贵的是**装卦断卦**（纳甲、六亲、世应、六神），且 200×200 的屏幕也放不下——一屏只够放六爻爻象、卦名、变卦名和一句短判断。**完整纳甲装卦不在本期范围内**，若需要应作为独立决策另行讨论。

## 5. 风险登记

| 风险 | 性质 | 应对 |
|---|---|---|
| 设备不常驻联网，无被动推送窗口 | **已确认为事实，非风险** | 已实测定论（§1.5）。架构已改为用户触发式，定时轮换与调度器全部移除。不要再尝试"后台自动推送"设计 |
| **推送内容是否作为待机画面留在屏幕上** | **阻断性，决定所有页面的体验等级** | 设备自身有每日运势等原生内容，是否覆盖自定义壁纸未知；离网后面板是否还刷新未知。由 Phase 0 三分支裁定：持久留存 / 仅短暂显示 / 完全不显示。仅最后一种需要全面停工 |
| 厂商云端是每次渲染的单点故障 | 高 | 缓存最后成功负载 + 失败退避。彻底解法是逆向 `COMPRESS_ARRAY_V2` 编码器（见 6） |
| 云端 API 无鉴权、限流未知 | 低（已大幅缓解） | 改为用户触发式后，请求量从预想的 144 次/日降到"每次用户主动推送 1 次"。按需渲染、不预取，进一步压低 |
| 设备 IP 由 DHCP 分配可能会变 | 低（观察未见发生） | 用户反馈 2026-07-29 当天多次开关设备联网，地址一直是 `192.168.3.235`，没有实测到漂移——多半是路由器 DHCP 租约在正常续租，但这只是当天的观察，不是"永不会变"的保证（路由器重启、租约到期等仍可能触发变化）。实测无 mDNS 主机名、无反向 DNS，MAC 是唯一稳定标识（本机为 `58:2a:bd:0a:98:c8`）。代码侧已实现的"IP 漂移自愈"（PLAN.md Phase 1，`device.resolve_ip_by_mac`）保留作为兜底，成本已付清，没有理由去掉；用户如果想更省心，仍可以在路由器上为这个 MAC 做静态绑定，但不是必须项 |
| 写入不可逆，无读回接口 | 中 | 服务侧保存每次推送的源图，形成可回滚的本地历史 |
| 用户误以为设备离线是故障 | 中 | 设备不可达是**常态**而非异常。所有推送入口都必须先探活并给出可操作提示（§3.3 第 2 条），不能暴露裸的连接超时 |
| 自动探测器与官方上传流程冲突 | 中 | 本期不做探测器（§3.1 末尾）。若日后补上，必须默认关闭并由用户显式布防 |
| 电量消耗不可测 | 低 | 内容未变不推送；用户触发式本身就把推送频率压到了最低 |

## 6. 后续路线（本期范围外）

**逆向 `COMPRESS_ARRAY_V2` 编码器**，摆脱对厂商云端的依赖。当前进展：观察到疑似行程编码（大量连续 `0xFF`）+ 一段疑似校验/签名的尾部字节（纯黑样本的尾部不遵循其他纯色样本"重复灰度值"的规律）。

卡点明确：判断尾部字节是否为设备端强制校验的签名，**必须真实写入设备验证**，而写入会覆盖当前壁纸且不可恢复。此项在完成基础功能、且用户愿意承担一次壁纸覆盖代价时再启动。
